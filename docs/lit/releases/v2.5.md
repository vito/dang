# v2.5.0 {#v2.5}

*Upgrading from v2.4.1: what breaks, how to fix it, and what to try.*

\lede{
Dang 2.5 is a new **language version**, and it changes how strings are
written. The delimiter now decides how a string's contents are read: double
quotes process escapes and interpolate `${...}`, the new single quotes are
verbatim, and backticks stay raw text with `${...}` for code. Quotes are for
text and backticks are for code. Code written for 2.4 can change meaning
under 2.5, so `dang migrate` rewrites it, keeping every string's value.
}

\table-of-contents

## Upgrade checklist {#v2.5-upgrade}

For a typical project, in order.

\steps{
  **Find out which language version your project gets** ([table
  below](#v2.5-versions)). A `dang.toml` without a `dang = "…"` key, or no
  `dang.toml` at all, now means 2.5.
}{
  **Migrate, or pin.** Preview with `dang migrate`, then write with `-w`. A
  project with no `dang` key that was written for 2.4 needs `--from 2.4`,
  because Dang can't tell. To stay on 2.4 for now, write `dang = "2.4"` in
  `dang.toml`; single-quoted strings still work there.

  ```sh
  dang migrate                    # preview what would change
  dang migrate -w                 # rewrite .dang files, bump dang.toml to "2.5"
  dang migrate -w --from 2.4 .    # for projects that never declared a version
  ```
}{
  **Check goldens of printed collections.** The REPL, `toString` and `print`
  now quote a string holding `${` with the `$` escaped, at every version
  ([details](#v2.5-repr)).
}

## Which language version you get {#v2.5-versions}

| Your project | Read as | `"${x}"` and `"""..."""` |
|---|---|---|
| `dang.toml` with `dang = "2.4"` (or older) | **2.4** | literal `${`; `"""` is raw |
| `dang.toml` without a `dang` key | **2.5** \pill{lang}{changed: was 2.4} | escapes and interpolation |
| no `dang.toml` (a lone script) | **2.5** | escapes and interpolation |
| new project from `dang init` | **2.5**, written as `dang = "2.5"` | escapes and interpolation |

Run without `--from`, `dang migrate` lists every project that declares no
version and suggests `--from`, as in [2.4](#v2.4-versions).

Dagger modules are the exception: Dagger's Dang SDK picks the version for a
module whose `dang.toml` declares none, from its `engineVersion` ([as in
2.4](#v2.4-dagger)). Such a module moves to 2.5 only once its engine embeds
Dang 2.5. Until then, don't migrate it: a `dang = "2.5"` is newer than its
engine's Dang, which is an error.

## What breaks, and how to fix it {#v2.5-breaking}

In order of how likely each is to hit existing code. Unless marked, examples
were run with Dang 2.5 and the output is quoted as printed.

### `"..."` interpolates `${...}` \pill{lang}{2.5 only} {#v2.5-interpolate}

At 2.4, a double-quoted string took `${` as text. At 2.5 it starts an
interpolation, as in a backtick template. Only `${` does, never a bare
`$name`, and `\$` escapes a dollar sign.

\pair{
  \pane{Before}{2.4}{
  ```dang
  let path = "${GOBIN}:${PATH}"
  let note = "it's ${HOME}\n"
  ```
  }
}{
  \pane{After}{dang migrate -w}{
  ```dang
  let path = '${GOBIN}:${PATH}'
  let note = "it's \${HOME}\n"
  ```
  }
}

\pane{The 2.4 spelling under 2.5}{
```error
Error: "HOME" not found
  --> /tmp/script.dang:1:10
     |
   1 | print("${HOME}")
                ^^^^
```
}

A name that happens to be in scope interpolates without an error, so read the
migration's diff rather than relying on the compiler.

\fix{
`dang migrate -w` turns a `"..."` holding `${` into a single-quoted string
where it can, and escapes the `$` where it can't (a string holding a `'` or
an escape). Shell-ish text like `.withEnvVariable("PATH",
'${GOBIN}:${PATH}', expand: true)` reads best in single quotes.
}

### `"""` processes escapes and interpolates \pill{lang}{2.5 only} {#v2.5-triple}

At 2.4, a `"""` string was raw: no escapes, no interpolation. At 2.5 it
follows the same rules as `"..."`, so a backslash in it is an escape, and an
unknown one is a syntax error. A `\n` or `\t` would silently become a newline
or a tab.

\pair{
  \pane{Before}{2.4}{
  ```dang
  let pattern = """\d+\.\d+"""
  let script = """
    echo "${HOME}" \
      done
  """
  ```
  }
}{
  \pane{After}{dang migrate -w}{
  ```dang
  let pattern = '''\d+\.\d+'''
  let script = '''
    echo "${HOME}" \
      done
  '''
  ```
  }
}

\fix{
`dang migrate -w` turns a `"""` string holding `\` or `${` into `'''`, which
is verbatim in every version. Where `'''` can't hold the text (it would end
the string early), it keeps `"""` and escapes the backslashes and dollar
signs instead. A `"""` with neither is left alone: it means the same thing at
both versions.
}

### A multi-line string's opening line holds at most a language tag \pill{lang}{2.5 only} {#v2.5-opening-line}

At 2.4, text could follow the opening `"""` or ```` ``` ```` and start the
value. At 2.5 the opening line of any multi-line string holds at most a
language tag (`"""sql`, `'''sh`, ```` ```go ````). Anything else there is an
error, unless the string closes on the same line (`"""inline"""`):

\pane{Text on the opening line under 2.5}{
```error
Error: syntax error: text on the opening line of a multi-line string: start it on the next line (only a language tag may follow the opening """, like """sh)
  --> /tmp/script.dang:1:7
     |
   1 | print("""Summary.
             ^^^^^^^^^^^
   2 | more
   3 | """)
```
}

A single word there is a tag, not text: at 2.4, `"""sql` followed by
`select` on the next line was `"sql\nselect"`, and at 2.5 it is `"select"`,
tagged `sql`.

\fix{
`dang migrate -w` moves text on an opening line to the next line, so
`"""sql` + `select` becomes a `"""` whose first line is `sql`. Docstrings are
not affected: they may still start on the opening line, and stay verbatim.
}

### Quoted strings escape `${` when printed \pill{all}{every version} {#v2.5-repr}

The REPL, `toString`, `print` and interpolation quote the strings inside a
collection as the Dang literal you'd write. Now that `"${` interpolates, they
escape it, so the output reads back as the same value. A string printed on
its own is still its bare text.

\pair{
  \pane{Program}{
  ```dang
  print(toString(['${HOME}']))
  print('${HOME}')
  ```
  }
}{
  \pane{Output}{
  ```output
  ["\${HOME}"]
  ${HOME}
  ```
  }
}

\fix{Update goldens that quote such strings.}

## What's new and worth trying {#v2.5-new}

### Verbatim strings: `'...'` and `'''...'''` \pill{new}{new} {#v2.5-single-quotes}

Single-quoted strings keep their text exactly as written: no escapes, no
interpolation. `'...'` can't hold a `'`; use another form for that. The
multi-line `'''` form dedents and takes a language tag like the others, which
suits shell scripts. Both work at every language version, 2.4 pins included.

\pair{
  \pane{Program}{
  ```dang
  print('C:\Users\${USER}')
  print('''sh
    for f in *.txt; do
      echo "${f%.txt}" \
        >> list
    done
  ''')
  ```
  }
}{
  \pane{Output}{
  ```output
  C:\Users\${USER}
  for f in *.txt; do
    echo "${f%.txt}" \
      >> list
  done
  ```
  }
}

### `"""` strings interpolate and take a language tag \pill{lang}{2.5 only} {#v2.5-cooked-triple}

A `"""` string dedents first and decodes its escapes after, so `\t` at the
start of a line is text, not indentation. The language tag tells editors how
to highlight the contents; it doesn't change the value.

\pair{
  \pane{Program}{
  ```dang
  let table = "users"
  let limit = 10
  print("""sql
    select name
    from ${table}
    limit ${limit}
  """)
  print("""
    \tindented with a tab
    costs \$5, not \${limit}
  """)
  ```
  }
}{
  \pane{Output}{
  ```output
  select name
  from users
  limit 10
  	indented with a tab
  costs $5, not ${limit}
  ```
  }
}

The full rules, side by side, are in [#literals].
