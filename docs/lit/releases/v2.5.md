# v2.5.0 {#v2.5}

*Upgrading from v2.4.1: what breaks, how to fix it, and what to try.*

\lede{
Dang 2.5 is a new **language version**, and it changes how strings are
written. The delimiter now decides how a string's contents are read: double
quotes process escapes and interpolate `${...}`, the new single quotes are
verbatim, and backticks stay raw text with `${...}` for code. Quotes are for
text and backticks are for code. Code written for 2.4 can change meaning
under 2.5, so `dang migrate` rewrites it, keeping every string's value.
At every version, interfaces declared in Dang are now structural: any type
with an interface's fields is a value of it, whichever schema it comes from,
so any value with a `message: String!` can be raised. A declaration may now
also take a snapshot of a binding that top-level statements write, errors for
habits from other languages come with a hint, Dagger modules run faster, and
Dang no longer needs cgo.
}

\table-of-contents

## Upgrade checklist {#v2.5-upgrade}

For a typical project, in order.

\steps{
  **Find out which language version your project gets** ([table
  below](#v2.5-versions)). A `dang.toml` without a `dang = "…"` key, or no
  `dang.toml` at all, now means 2.5.
}{
  **Migrate, or pin.** Preview with `dang migrate`, then write with `-w`. A
  project with no `dang` key that was written for 2.4 needs `--from 2.4`,
  because Dang can't tell. To stay on 2.4 for now, write `dang = "2.4"` in
  `dang.toml`; single-quoted strings still work there.

  ```sh
  dang migrate                    # preview what would change
  dang migrate -w                 # rewrite .dang files, bump dang.toml to "2.5"
  dang migrate -w --from 2.4 .    # for projects that never declared a version
  ```
}{
  **Check goldens of printed collections.** The REPL, `toString` and `print`
  now quote a string holding `${` with the `$` escaped, at every version
  ([details](#v2.5-repr)).
}{
  **Run it.** A `case` or `rescue` arm that follows an arm on a Dang
  interface may now be unreachable, because the interface's arm takes every
  type of its shape; put the specific arms first
  ([details](#v2.5-structural-patterns)).
}

## Which language version you get {#v2.5-versions}

| Your project | Read as | `"${x}"` and `"""..."""` |
|---|---|---|
| `dang.toml` with `dang = "2.4"` (or older) | **2.4** | literal `${`; `"""` is raw |
| `dang.toml` without a `dang` key | **2.5** \pill{lang}{changed: was 2.4} | escapes and interpolation |
| no `dang.toml` (a lone script) | **2.5** | escapes and interpolation |
| new project from `dang init` | **2.5**, written as `dang = "2.5"` | escapes and interpolation |

Run without `--from`, `dang migrate` lists every project that declares no
version and suggests `--from`, as in [2.4](#v2.4-versions).

Dagger modules are the exception: Dagger's Dang SDK picks the version for a
module whose `dang.toml` declares none, from its `engineVersion` ([as in
2.4](#v2.4-dagger)). Such a module moves to 2.5 only once its engine embeds
Dang 2.5. Until then, don't migrate it: a `dang = "2.5"` is newer than its
engine's Dang, which is an error.

## What breaks, and how to fix it {#v2.5-breaking}

In order of how likely each is to hit existing code. Unless marked, examples
were run with Dang 2.5 and the output is quoted as printed.

### `"..."` interpolates `${...}` \pill{lang}{2.5 only} {#v2.5-interpolate}

At 2.4, a double-quoted string took `${` as text. At 2.5 it starts an
interpolation, as in a backtick template. Only `${` does, never a bare
`$name`, and `\$` escapes a dollar sign.

\pair{
  \pane{Before}{2.4}{
  ```dang
  let path = "${GOBIN}:${PATH}"
  let note = "it's ${HOME}\n"
  ```
  }
}{
  \pane{After}{dang migrate -w}{
  ```dang
  let path = '${GOBIN}:${PATH}'
  let note = "it's \${HOME}\n"
  ```
  }
}

\pane{The 2.4 spelling under 2.5}{
```error
Error: "HOME" not found; to write ${HOME} as text, single-quote the string or escape it as \${HOME}
  --> /tmp/script.dang:1:10
     |
   1 | print("${HOME}")
                ^^^^
```
}

A name that happens to be in scope interpolates without an error, so read the
migration's diff rather than relying on the compiler.

\fix{
`dang migrate -w` turns a `"..."` holding `${` into a single-quoted string
where it can, and escapes the `$` where it can't (a string holding a `'` or
an escape). Shell-ish text like `.withEnvVariable("PATH",
'${GOBIN}:${PATH}', expand: true)` reads best in single quotes.
}

### `"""` processes escapes and interpolates \pill{lang}{2.5 only} {#v2.5-triple}

At 2.4, a `"""` string was raw: no escapes, no interpolation. At 2.5 it
follows the same rules as `"..."`, so a backslash in it is an escape, and an
unknown one is a syntax error. A `\n` or `\t` would silently become a newline
or a tab.

\pair{
  \pane{Before}{2.4}{
  ```dang
  let pattern = """\d+\.\d+"""
  let script = """
    echo "${HOME}" \
      done
  """
  ```
  }
}{
  \pane{After}{dang migrate -w}{
  ```dang
  let pattern = '''\d+\.\d+'''
  let script = '''
    echo "${HOME}" \
      done
  '''
  ```
  }
}

\fix{
`dang migrate -w` turns a `"""` string holding `\` or `${` into `'''`, which
is verbatim in every version. Where `'''` can't hold the text (it would end
the string early), it keeps `"""` and escapes the backslashes and dollar
signs instead. A `"""` with neither is left alone: it means the same thing at
both versions.
}

### A multi-line string's opening line holds at most a language tag \pill{lang}{2.5 only} {#v2.5-opening-line}

At 2.4, text could follow the opening `"""` or ```` ``` ```` and start the
value. At 2.5 the opening line of any multi-line string holds at most a
language tag (`"""sql`, `'''sh`, ```` ```go ````). Anything else there is an
error, unless the string closes on the same line (`"""inline"""`):

\pane{Text on the opening line under 2.5}{
```error
Error: syntax error: text on the opening line of a multi-line string: start it on the next line (only a language tag may follow the opening """, like """sh)
  --> /tmp/script.dang:1:7
     |
   1 | print("""Summary.
             ^^^^^^^^^^^
   2 | more
   3 | """)
```
}

A single word there is a tag, not text: at 2.4, `"""sql` followed by
`select` on the next line was `"sql\nselect"`, and at 2.5 it is `"select"`,
tagged `sql`.

\fix{
`dang migrate -w` moves text on an opening line to the next line, so
`"""sql` + `select` becomes a `"""` whose first line is `sql`. Docstrings are
not affected: they may still start on the opening line, and stay verbatim.
}

### Quoted strings escape `${` when printed \pill{all}{every version} {#v2.5-repr}

The REPL, `toString`, `print` and interpolation quote the strings inside a
collection as the Dang literal you'd write. Now that `"${` interpolates, they
escape it, so the output reads back as the same value. A string printed on
its own is still its bare text.

\pair{
  \pane{Program}{
  ```dang
  print(toString(['${HOME}']))
  print('${HOME}')
  ```
  }
}{
  \pane{Output}{
  ```output
  ["\${HOME}"]
  ${HOME}
  ```
  }
}

\fix{Update goldens that quote such strings.}

### Type patterns on Dang interfaces match by shape \pill{all}{every version} {#v2.5-structural-patterns}

Interfaces declared in Dang are now structural ([below](#v2.5-structural)),
at every language version, since every version runs on the same
interpreter. Most code that compiled still compiles and means the same:
values that used to be refused now pass. Two kinds of `case` and `rescue`
can change:

- An arm on a type that has an interface's shape, after an arm on that
  interface, is now unreachable, an error: the interface's arm takes that
  type's values first.
- An arm on an interface now takes a value whose type only has the shape,
  where it used to fall through to a later arm or `else`. This needs an
  operand that holds a declared implementation as well, since a pattern
  nothing could match was an error before.

\fix{
Put the arms for specific types first. Where an arm on an interface must
not take a type of its shape, match that type before it.
}

## What's new and worth trying {#v2.5-new}

### Structural interfaces, across schemas \pill{new}{new} {#v2.5-structural}

An interface declared in Dang is satisfied by any type with its fields,
public and of fitting types, whether or not the type says `implements`, and
whichever schema it comes from. Interfaces a GraphQL schema declares stay
nominal. The prelude's `Error` is one, so any type with a `message: String!`
can be raised, a schema's own error type included: in a Dagger module, a
`Dagger.Error` raises and rescues as an `Error`, and the host gets the very
object raised, values and all. See [#structural-interfaces].

\pair{
  \pane{Program}{
  ```dang
  interface Named {
    name: String!
  }

  type Person {
    name: String!
  }

  type Oops {
    message: String!
    code: Int!
  }

  greet(n: Named!): String! { `hello, ${n.name}` }

  print(greet(Person("Ada")))
  print({ raise Oops("boom", 7) } rescue {
    e: Error! => e.message
  })
  ```
  }
}{
  \pane{Output}{
  ```output
  hello, Ada
  boom
  ```
  }
}

A rescued error raised again as it was keeps the error it was made of
(`RaisedError.Origin`), so a host can report it as it would have had nothing
rescued it: the GraphQL error behind a `GraphQLError`, extensions and all.

### Verbatim strings: `'...'` and `'''...'''` \pill{new}{new} {#v2.5-single-quotes}

Single-quoted strings keep their text exactly as written: no escapes, no
interpolation. A `'` would end `'...'`, so text holding one goes in
`'''...'''`, which can hold quotes even on one line (`'''it's'''`). The
multi-line `'''` form dedents and takes a language tag like the others, which
suits shell scripts. Both work at every language version, 2.4 pins included.

\pair{
  \pane{Program}{
  ```dang
  print('C:\Users\${USER}')
  print('''sh
    for f in *.txt; do
      echo "${f%.txt}" \
        >> list
    done
  ''')
  ```
  }
}{
  \pane{Output}{
  ```output
  C:\Users\${USER}
  for f in *.txt; do
    echo "${f%.txt}" \
      >> list
  done
  ```
  }
}

### `"""` strings interpolate and take a language tag \pill{lang}{2.5 only} {#v2.5-cooked-triple}

A `"""` string dedents first and decodes its escapes after, so `\t` at the
start of a line is text, not indentation. The language tag tells editors how
to highlight the contents; it doesn't change the value.

\pair{
  \pane{Program}{
  ```dang
  let table = "users"
  let limit = 10
  print("""sql
    select name
    from ${table}
    limit ${limit}
  """)
  print("""
    \tindented with a tab
    costs \$5, not \${limit}
  """)
  ```
  }
}{
  \pane{Output}{
  ```output
  select name
  from users
  limit 10
  	indented with a tab
  costs $5, not ${limit}
  ```
  }
}

The full rules, side by side, are in [#literals].

### Declarations can snapshot statement-written state \pill{all}{every version} {#v2.5-snapshots}

2.4 rejected every read, from a declaration's initializer, of a binding that
top-level statements write. A declaration that reads it before every write
now works, and sees the value from before the writes, as its place in the
source says. The read must be written directly in the initializer (not in a
block argument, a `{{ }}` field or a function) and every write must be in the
same file.

\pair{
  \pane{Program}{
  ```dang
  let count = 1
  let first = count
  count += 1
  count += 1
  print([first, count])
  ```
  }
}{
  \pane{Output}{
  ```output
  [1, 3]
  ```
  }
}

A read after a write would be misleading, so it is still an error, as is any
read from a function:

\pane{Read after a write}{
```error
Error: `latest`'s initializer reads `total`, which a top-level statement writes (line 2), but top-level declarations run before top-level statements, so it would see the value from before the write; read `total` in a top-level statement instead, or compute it in a declaration rather than writing it from statements
  --> /tmp/script.dang:3:14
     |
   1 | let total = 1
   2 | total += 1
   3 | let latest = total
                    ^^^^^
```
}

The rules are in [#top-level-bindings].

### Hints for common mistakes \pill{all}{every version} {#v2.5-pitfalls}

Some errors come from habits other languages teach. Dang now recognizes a few
of them precisely and adds a one-line hint and a link to the docs, in the CLI,
the LSP, the REPL and the playground: `//` comments, `&&` and `||`, `for` and
`while` loops, `{a: 1}` records, and non-Boolean conditions. Look-alike code
that isn't the mistake, like `n // 2` written by a Python habit, is left alone.

\pair{
  \pane{Program}{
  ```dang
  let a = true
  let b = false
  print(a && b)
  ```
  }
}{
  \pane{Output}{
  ```error
  Error: syntax error: `&&` is not an operator
    --> /tmp/script.dang:3:9
       |
     1 | let a = true
     2 | let b = false
     3 | print(a && b)
                 ^^
       |
       = hint: the logical operators are the keywords `and` and `or` (and `!` to negate)
       = docs: https://danglang.org/operators#logical
  ```
  }
}

\pane{No truthiness}{
```error
Error: condition must be Boolean!, got Int!
  --> /tmp/script.dang:2:5
     |
   1 | let n = 3
   2 | if (n) { print("yes") }
           ^
     |
     = hint: there is no truthiness: test explicitly, e.g. `x != null` or `!xs.isEmpty`
     = docs: https://danglang.org/control-flow#if-else
```
}

### Smaller changes {#v2.5-smaller}

- **Dagger modules run faster.** When a call's argument is an object that
  needs its own request to get an ID (for a Dagger module function, running
  the function), the call's receiver now runs at the same time, rather than
  after it. A module that installs system packages while it builds four Go
  tools went from 37.4 s to 27.2 s on a fresh engine. Nothing changes in
  meaning; the first failure stops the other side and is the one reported.
- **A failed declaration is reported once.** Every later use of a `let` that
  failed to type-check used to add an error of its own, `"c" not found` or a
  confusing internal one. Now only the original error is reported, and a
  declaration with an annotation or a declared signature still checks its
  uses against that type.
- **GraphQL object list hints** suggest `value.{{id}}`, not the 1.x
  `value.{id}`: `cannot select "name" from a GraphQL object list; select
  fields on its elements first, e.g. value.{{id}}`.
- **Editors.** The tree-sitter grammar knows every string form: `${...}`
  inside `"..."` and `"""` highlights as code, a `#` inside any string is
  text, and a language tag on `"""` or `'''` highlights the contents in that
  language, as on backtick fences. Completion works inside `${...}` and stays
  quiet in string text. Zed and Neovim get this with their extensions' next
  update. VSCode's grammar knows the new strings and marks the tag, but
  doesn't highlight the contents in the tagged language. Editors always
  follow the 2.5 rules, so in a project pinned to 2.4, `"${x}"` highlights as
  an interpolation even though it is text there.
- **Syntax errors** point nearer the mistake in a few cases: `%raw{x}` now
  says `unexpected '%'` at the `%`, rather than underlining the whole line,
  and an error is reported where parsing failed rather than at the first
  thing tree-sitter found odd in the file.

## Go embedders \pill{go}{Go API} {#v2.5-embedders}

| Removed or changed | Use instead |
|---|---|
| `dang.CurrentVersion` is now `dang.Version2_5` | `dang.Version2_4` where you mean a fixed version; `ContextWithVersion` to pin a module, unchanged |
| Every `"..."` literal parses to a `*dang.String` | At 2.5, one that interpolates is a `*dang.Template` with `Quote == '"'`. `*dang.String` gains `Quote`, `Verbatim` and `Lang`, which record spelling only |
| Tree-sitter through cgo and `github.com/tree-sitter/go-tree-sitter` | Nothing: tree-sitter now runs as WebAssembly, under wazero |

**No more cgo.** Dang's tree-sitter is compiled to WebAssembly
(`pkg/dang/tswasm`), so completion, the LSP, `analysis.Complete`, REPL
highlighting and precise parse errors all work in `CGO_ENABLED=0` builds,
the Dagger engine's included. The first use compiles the module, about 50 ms,
and caches it (about 800 KB, under the user cache directory's
`dang/wazero`), so later processes take about 2 ms. Call
`dang.LoadTreeSitter()` to compile it ahead of the first request, as the LSP
does on `initialize`. Completion now reparses an edited document
incrementally, so it is faster than before on large files.

New: `analysis.Options{DiagnosticContext: true}` fills
`Diagnostic.Context` for type errors about a name: the closest names by
spelling, the receiver's members, and docs that mention it. It is off by
default and costs nothing when off. `analysis.Render` and `Diagnostic.Format`
print diagnostics with that context:

```output
main.dang:2:1: error: list does not have method "findFirst"
  closest: find { item: a => Boolean! }: a?  returns the first element for which the predicate returns true, or null if none…
  [String!]! has 25 members: all any contains dropFirst dropLast dropWhile each filter find flatMap
    indexOf isEmpty join length map reduce reject reverse sort sortBy sum takeFirst takeLast
    takeWhile uniq
```

\sourced{Quoted from #298's description; no CLI prints this yet.}

`Module.Eval` and `Session` snippets accept [declaration
snapshots](#v2.5-snapshots) too, and give the same values a script would.

A rescued error raised again unchanged keeps the Go error it was classified
from, as `RaisedError.Origin()`, so a host can report, say, the GraphQL error
behind a `GraphQLError` with its extensions. It is deliberately not `Unwrap`,
which would let `errors.As` find the original failure's source location
instead of the raise site.
